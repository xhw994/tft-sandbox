# 让 TFT 推荐更安全、更可解释

**当前脚本已具备可用的手动棋盘、规则校验与启发式推荐，不需要推倒重写；最值得优先改的是推荐的安全边界与解释能力。** 棋子费用、角色标签和羁绊分数不能代替战斗模拟，若在替换、追三星和角色识别中口径不一，就可能把局部加分误当成可靠升级。建议先将风险门槛和策略偏好做成显式规则，再共享羁绊评估、补齐数据来源与 UI 说明，最后基于基准数据优化计算。审阅只读静态代码，未运行测试，也未实测性能；游戏数值数据来源为项目 Set19 的 tftTest 与 Data Dragon 16.23.1，不能据此称为当前 live 数据。

## 先统一候选资格与换牌风险，再比较总分

现有结构以 `index.html` 的 classic scripts/file:// 入口为基础：`engine.js` 负责评估、搜索与推荐，`board.js` 集中棋盘状态转换和校验，`app.js` 管理交互、存档和渲染，`build_data.py` 生成静态数据。保留这条轻量路径及 `TFTBoard.apply/normalize` 边界，比引入框架或 bundler 更稳妥。已有代码也有值得保留的基础：棋盘动作验证重叠格、双格棋子与装备约束，替换流程迁移装备/站位并处理不兼容物品；这些可作为推荐改造的安全底座。（项目审阅：`engine.js`、`board.js`、`app.js`、`index.html`）

最高优先级是把**资格检查与损失风险放在总分比较之前**，并让 core、full swaps、坦克重排和方案推荐共用同一套可解释门槛。至少显式检查降星、关键前排/主C职责、羁绊档位是否失活、装备迁移及不兼容；再展示人数变化、档位效果变化和理由。当前 `traitChangesOf()` 只记录人数，`swapCard()` 未呈现 `s.reasons`，用户难以判断加分来自什么、代价是什么。避免将所有因素混成一个分数：通过门槛后才按不同策略目标排序，并把风险标签与收益分开呈现。

坦克判定尤其应按设计意图修正：`realTank(unit,ctx)` 目前要求 `role === tank && cost >= curve.floor`，不看星级或装备，因此低费三星坦克可能被排除。若这里要判断实际前排承载，应让星级、装备与防御属性参与；若表达的是“符合当前费用曲线的坦克”，则应另设资格名称，不能把它当作真实承载能力。类似地，`carryScore` 用费用、攻击力/攻速和角色权重，无法有意义地推断施法伤害。应将角色资格、投资优先级、能力信号和不确定性分开；不要伪装成战斗模拟或胜率预测。

## 把追三星作为偏好，而非游戏定律

自动追三星（2★→3★）候选应只纳入 1–3 费；4/5 费追二星仍允许，手动已有高费三星也应保留、识别和分析。现有 reroll 引擎限于 cost≤3，但 `starUps()` 面向已上场棋子，应区分“自动追三星资格”和“阵容状态展示”，避免过滤规则误伤玩家已有状态。5级追1/2费、6级追2/3费、7级追3费适合作为可配置策略模板，而非不随局势变化的通用定律；呈现偏好来源并允许关闭或调整。

经济、升级、刷新和购买争用同一有限资源，羁绊断点与单位替换又会改变目标价值。Riot 对 TFT 的基础介绍强调共享棋池、经济管理、阵容构筑和适应局势，补丁说明也展示玩法与平衡随赛季更新（[TFT 基础介绍](https://teamfighttactics.leagueoflegends.com/en-us/news/game-updates/what-is-teamfight-tactics/)，[16.1 补丁说明](https://teamfighttactics.leagueoflegends.com/en-us/news/game-updates/teamfight-tactics-patch-16-1)）。当前资料不足以确认完整现行经济规则、单位剩余池或对手持有量，所以不要从费用档商店概率推导单一英雄命中率，也不要输出“刷几次必出”。若将来支持备战规划，可先让用户手动输入经济、已有副本、回合/等级和目标，分别比较保留金币、升级、刷新等方案；对缺失的共享池信息明确标注未知，而不是填入假精确值。

## 先补 UI 与数据可信度，再做性能优化

UI 尚有明确的呈现改进：选中边框用 `--accent`，而根样式中的金色变量为 `#e0a04a`，选中样式又覆盖了费用边框；应统一设计 token 与选择态，同时保留费用颜色。羁绊按钮目前**没有实现 on/unmet/target 的铜、银、金、棱彩档位色**，应按实际羁绊层级/激活状态实现，并兼顾色盲与文字标签。三星星号目前横向重复显示且仅 11px，应放大并将三星改为三角形呈现；装备槽目前用白点表示，应改为使用现有装备图标缩略图。换牌卡片还应补显示理由、档位得失与装备处理。（项目审阅：`styles.css`、`app.js`）

数据应携带来源、抓取时间、目标补丁、测试/live 状态与 schema 版本，并按赛季/自定义数据身份隔离存档，导入时校验唯一 ID、引用完整性并给出字段定位诊断。当前项目混用 tftTest 静态数据与 Data Dragon 16.23.1；Riot 文档说明 19.1（2026-12-01）起将切换数据管线并影响文件路径、标识符、schema 和图像等，因此迁移前不应标作已验证 live，并应在切换时逐项验证兼容性（[Riot TFT 开发者文档](https://developer.riotgames.com/docs/tft)）。

性能改进放在基准之后：先记录固定棋盘/搜索规模下的耗时与节点数，再看 `evaluate()`、分类和 beam search 重复计算是否值得在**单次分析内**缓存共享结果。不要先做全局缓存或推测卡顿；推荐流程可渐进接入已有可取消、分片的 `track()` task 与 generation guard，避免过期结果覆盖新棋盘。保留窄范围、行为导向测试；优先覆盖低费三星不被降星替换、自动追三星不推荐4/5费、4/5费追二星仍允许、手动已有高费三星保留、羁绊档位损失可见、装备守恒和旧任务结果丢弃。以上为建议测试，当前未运行测试。

## 结论

最有效的下一步不是复杂化评分，而是让工具先能安全地拒绝不合理候选、诚实表达不知道，并说明每个建议的代价。以共享的资格/风险契约作为第一步，之后再补策略偏好、数据版本和 UI 解释，既可扩展，又能维持现有 file:// 工作流与轻量结构。若公开发布，应保持手动规划与复盘定位，并在发布前复核 Riot 对第三方 TFT 产品的注册及实时辅助政策（[开发者政策](https://developer.riotgames.com/docs/tft)）。
